# CBL-C Language and Lowering Design Document

*Last updated: 2026-07-08*

## 1. Purpose

CBL-C is the source language accepted by this repository. It is intentionally smaller than C or C++, but it is not a toy syntax layer. The language must be:

- Stable enough to round-trip between CBL-C and COBOL for the supported subset.
- Strict enough that the same source always lowers to the same program structure.
- Small enough that every language feature has one canonical semantic meaning.
- Explicit enough that code generation can be implemented by reusable lowering rules instead of pasted one-off code chunks.

This document is the implementation contract for the language. It describes:

- What is allowed.
- What is not allowed.
- What each construct must lower into.
- How classes, built-in `string`, and standard-library calls must behave.

## 2. Design Rules

### 2.1 Canonical form

Each language feature must have one canonical source form and one canonical lowering strategy.

- If the parser accepts a construct, the backend must define its exact meaning.
- If the backend cannot lower a construct reliably, the parser must reject it.
- If a feature can be expressed in multiple ways, the project must still choose one preferred form for emitted code.

### 2.2 No code duplication as a language rule

The implementation must not solve a language feature by pasting the same semantic expansion into multiple emitters.

- Shared lowering logic belongs in shared helpers.
- Shared runtime behavior belongs in runtime helpers or standard-library subprograms.
- Class and string behavior must be derived from reusable object rules, not from emitted ad hoc code fragments.

This matters most for:

- Built-in `string`.
- Constructors and destructors.
- Method calls on instances.
- Standard-library wrappers.
- Return-slot handling for non-void functions and struct-returning functions.

### 2.3 Allowed by default, disallowed by omission

CBL-C is a closed language subset.

- If a syntax form is not documented here or in the grammar, it is not part of the language.
- If a COBOL or C++ concept is not modeled here, it is out of scope even if the parser could recognize it.
- If a source form depends on undefined ordering or side effects, it is disallowed.

## 3. Program Shape

A translation unit is organized into:

1. Global declarations.
2. Function definitions.
3. Optional class and struct declarations that introduce record-like data and methods.

The source language is not free-form C++. It is a typed, restricted language designed to lower deterministically.

### Allowed

- Global scalars.
- Global arrays.
- Records and structs.
- Classes with members, constructors, methods, and optional destructor-like lifecycle hooks.
- Function definitions.
- Statements inside blocks.

### Not allowed

- Arbitrary templates.
- Operator overloading.
- Inheritance.
- Virtual dispatch.
- Lambdas.
- Exceptions.
- Namespaces beyond the limited `std::` and `cblc::` standard-library surface already supported.
- Arbitrary preprocessor logic as a language feature.

## 4. Type Model

CBL-C uses a small number of type families:

- Numeric scalars.
- Boolean scalars.
- Fixed-size character buffers.
- Built-in `string`.
- Records and structs.
- Classes.
- Pointers where explicitly supported by the current backend.

### 4.1 Scalar policy

Numeric and boolean scalars must map to the backend storage type selected by the compiler’s current policy. The exact COBOL picture or C storage must be derived from the type descriptor, not hard-coded per call site.

### 4.2 Fixed-size text policy

Fixed-size text is not a heap string model.

- `char[n]` means a fixed buffer of `n` bytes.
- `string(n)` means the built-in `string` object with capacity `n`.
- String truncation must be validated and reported, not silently ignored.

### 4.3 Records and structs

Records and structs are data-only aggregates.

- Fields are stored in declaration order.
- Field layout must remain stable across lowering.
- Nested members are allowed when the backend can preserve the member path.

## 5. Functions

Functions are the primary executable unit.

### Allowed

- `void` functions.
- Value-returning functions.
- Parameter lists.
- Local block scope.
- `return;` in `void` functions.
- `return expr;` in value-returning functions.

### Disallowed

- Multiple incompatible definitions with the same signature in the same translation unit.
- Implicit returns from non-void functions.
- Falling off the end of a non-void function without an explicit return slot strategy.

### Lowering rule

Every function must lower into a stable callable unit in the target.

- In COBOL, this means a paragraph or equivalent call target with explicit parameter and return storage.
- In C, this means a generated function plus any required helper storage.

## 6. Class Model

Classes are the main abstraction layer above records. A class is not a runtime object system. It is a compile-time model for grouped storage plus named operations.

### 6.1 What a class is

A class introduces:

- Member storage.
- Constructor overloads.
- Optional destructor-like cleanup behavior.
- Methods callable on an instance.
- Optional const enforcement on members and member access.

### 6.2 What a class is not

A class is not:

- A virtual inheritance hierarchy.
- A polymorphic runtime with vtables.
- A general-purpose C++ feature set.
- A container for arbitrary code that bypasses the lowering rules.

### 6.3 Member visibility

The current model supports public and private member groupings.

- Public members are callable or readable where the parser and semantic pass allow them.
- Private members are only accessible where the class rules allow it.
- Access checks are semantic, not stylistic.

### 6.4 Constructors

Constructors define how an instance is initialized.

Allowed forms:

- Zero-argument constructor.
- Parameterized constructor.
- Overloaded constructors by arity.
- Copy-constructor style overloads where supported by the parser and semantic analysis.

Required behavior:

- Construction must initialize member storage deterministically.
- Constructor arguments must be lowered into named parameter storage before the body runs.
- Constructor bodies must run after parameter assignment and before the instance is considered usable.

Example:

```cblc
class Counter
{
    public:
    int value;
    Counter();
    Counter(int start);
};

Counter::Counter()
{
    value = 1;
}

Counter::Counter(int start)
{
    value = start;
}
```

Expected lowering:

- One zero-argument lifecycle body.
- One one-argument lifecycle body.
- Distinct parameter storage for the overloads.
- Instance initialization occurs through the selected constructor body.

### 6.5 Methods

Methods are instance-bound functions.

Allowed forms:

- `void` methods.
- Value-returning methods.
- Struct-returning methods where the backend already supports them.
- Inline method bodies inside the class.
- Out-of-class qualified method definitions.

Required behavior:

- The receiver must be explicit in lowering.
- `object.method(args)` must become a call or inlined expansion that operates on `object`.
- Qualified definitions must bind to the class that declared the signature.

Example:

```cblc
class Counter
{
    public:
    int value;
    void reset();
    int current();
};

void Counter::reset()
{
    value = 0;
    return;
}

int Counter::current()
{
    return value;
}
```

Expected lowering:

- `counter.reset()` becomes a receiver-aware call.
- `counter.current()` becomes a receiver-aware value-producing call.
- The generated target code must reference the receiver storage directly, not duplicate the body inline in unrelated locations.

### 6.6 Lifecycle hooks

The current implementation treats constructor and destructor-style behavior as lifecycle hooks.

Allowed:

- Automatic constructor entry.
- Automatic destructor entry at scope exit when the object is local.
- Custom constructor and destructor bodies.
- Empty lifecycle hooks when no body is defined.

Required behavior:

- Local class instances must receive initialization before first use.
- Local class instances must be cleaned up before the enclosing scope exits.
- Lifecycle code must be emitted in the same order as source scope lifetime.

### 6.7 Class expansion standard

Class lowering must follow this pattern:

1. Record the class declaration once.
2. Record constructor and method signatures once.
3. Bind member references through the instance path.
4. Lower constructor calls into parameter assignment plus lifecycle body execution.
5. Lower method calls into receiver-bound execution.
6. Lower destructor-like cleanup at scope exit.

This standard exists so classes are not lowered by pasting code blocks into every call site.

## 7. Built-in `string`

`string` is a built-in type with special semantics. It is not just a `char[]` alias.

### 7.1 Object model

The built-in string object is conceptually:

- A length field.
- A backing buffer.
- A fixed capacity.

The exact emitted representation varies by backend, but the semantics do not.

### 7.2 Allowed forms

- `string name(16);`
- `string name("literal");`
- `string copy(otherString);`
- `string array[4](12);`
- `const string greeting(12) = "HELLO";`

### 7.3 Disallowed forms

- `string name[16];` using bracket capacity syntax.
- Treating `string` as a raw C pointer.
- Mutating a const string after initialization.
- Writing string logic by manually copying the same buffer-handling code into each method body.

### 7.4 String semantics

The following operations are part of the built-in model:

- Assignment from a literal.
- Assignment from another string.
- Append.
- Clear.
- Length query.
- Capacity query.
- Empty check.
- Equality.
- Compare.
- Contains.
- Starts-with.
- Ends-with.

For compatibility with recovered source and existing tests, some accessors may appear in both field-style and call-style forms. The semantic rule is the same in either case:

- `len` or `len()` reads the stored length.
- `capacity` or `capacity()` returns the declared capacity.

Example:

```cblc
void main()
{
    string greeting(8);
    string suffix(4);
    greeting = "HI";
    suffix = "!";
    greeting.append(suffix);
    display(greeting.len);
    display(greeting.capacity());
    display(greeting.empty());
    return;
}
```

Expected lowering:

- `len` reads the stored length.
- `capacity` returns the declared capacity.
- `clear` resets the buffer and length.
- `append` copies the source text into the destination according to capacity rules.
- Predicate methods lower into boolean-producing helper logic.

### 7.5 String lowering standard

String support must be implemented once as a shared object model.

- C backend should call string helper routines.
- COBOL backend should emit buffer and length operations through shared helper logic or generated statements, not by duplicating the same handwritten sequence at every call site.
- Standard-library string functions should be routed through the catalog in `src/standard_library`, not expanded as inline copies of helper bodies.

This is the main rule that prevents the current "paste the same chunk again" problem.

## 8. Standard Library

Standard-library functions are part of the language contract, not just convenient helpers.

### 8.1 Qualified naming

Supported names include the current `std::` and `cblc::` catalog entries already wired into the transpiler.

### 8.2 Lowering rule

Each standard-library function must map to a named helper entry with a stable contract.

Examples:

- `std::strlen` maps to the string-length helper.
- `std::strcpy` maps to the copy helper.
- `std::strcmp` maps to the compare helper.
- `std::strcat` maps to the concat helper.
- `std::atoi`, `std::atol`, and `std::atoll` map to conversion helpers.
- `std::toupper` and `std::tolower` map to case conversion helpers.

### 8.3 Buffer specialization

Many standard-library helpers have multiple lowering forms.

- One form operates on raw character buffers.
- One form operates on built-in string objects.

These are distinct lowering targets because the calling convention differs. They should remain in the standard-library catalog rather than being reimplemented ad hoc.

## 9. Statements

### Allowed statements

- Assignment.
- `if` / `else`.
- `while`.
- `perform` when supported by the recovered COBOL subset.
- Function calls.
- Method calls.
- `open`, `close`, `read`, `write`, and `display` where supported.
- `return`.
- Empty statement `;`.

### Disallowed statements

- Unscoped jump semantics.
- Goto-style control flow in the CBL-C surface.
- Multi-target assignments unless explicitly defined by the lowering rule.
- Ambiguous use of `=` for equality.

### Assignment rule

`=` means assignment.

- `==` means equality comparison.
- `!=` means inequality comparison.

This is a hard rule and must not vary by context.

## 10. Control Flow

### If

```cblc
if (cond) {
    display("then");
} else {
    display("else");
}
```

Lowering expectation:

- Emit a single conditional structure.
- Preserve then/else structure.
- Do not flatten both branches into repeated inline fragments.

### While

```cblc
while (read(input, line)) {
    write(output, line);
}
```

Lowering expectation:

- Use a loop construct that preserves the read test.
- Prefer a structured `PERFORM UNTIL`-style emission in COBOL.
- Keep the read/EOF semantics explicit.

### Perform

`perform` is supported only where the parser and emitter can resolve a valid target. It is not a substitute for arbitrary function calls.

## 11. Files and I/O

The current pipeline supports the recovery and generation of selected file-style operations.

### Allowed

- `file` declarations with the supported modes.
- `open(file, mode)`.
- `read(file, value)`.
- `write(file, value)`.
- `close(file)`.

### Disallowed or partial

- Arbitrary COBOL file-control layout that the backend cannot generate faithfully.
- File features not represented by the current runtime and emitter.

The project already treats forward file-control emission as partial, so new file features must be added with tests and explicit lowering rules.

## 12. Lowering Contract

Every language feature must satisfy the same lowering contract:

1. Parse the source form.
2. Classify the source form semantically.
3. Validate type, scope, and access constraints.
4. Choose a canonical lowering strategy.
5. Emit target code using shared helpers or named helper programs.
6. Verify the generated shape with tests.

### Required evidence for a new feature

- Grammar update if syntax changed.
- Semantic tests for allowed and disallowed cases.
- Generation tests for C and COBOL if the feature lowers to both.
- Runtime or standard-library tests if the feature depends on helper behavior.

## 13. Examples

### 13.1 Allowed class usage

```cblc
class Counter
{
    public:
    int value;
    Counter(int start);
    void add(int delta);
    int current();
};

Counter::Counter(int start)
{
    value = start;
}

void Counter::add(int delta)
{
    value = value + delta;
    return;
}

int Counter::current()
{
    return value;
}

void main()
{
    Counter counter(4);
    counter.add(5);
    display(counter.current());
    return;
}
```

Expected result:

- Constructor parameter storage is created once.
- `counter` is initialized before use.
- `add` and `current` are receiver-bound.
- `display` receives the value produced by the call.

### 13.2 Allowed string usage

```cblc
void main()
{
    string greeting(8);
    string suffix(4);
    greeting = "HI";
    suffix = "!";
    greeting.append(suffix);
    display(greeting.len);
    return;
}
```

Expected result:

- `greeting` and `suffix` are backed by fixed-capacity string objects.
- `append` does not paste a custom buffer-copy chunk into the call site.
- `len` is read from object state, not recomputed from scratch in every caller.

### 13.3 Disallowed string syntax

```cblc
string greeting[16];
```

This is invalid because string capacity uses parentheses, not bracket syntax.

### 13.4 Disallowed semantic ambiguity

```cblc
if (a = b) {
    display("bad");
}
```

This is invalid because `=` is assignment, not comparison.

## 14. Implementation Standard

The codebase should obey the following implementation standard:

- One feature, one lowering rule.
- One runtime behavior, one helper API.
- One standard-library contract, one generated helper program.
- One class lifecycle rule, one constructor/destructor path.
- One string object model, one shared set of buffer operations.

Any new feature must answer these questions before it lands:

1. What is the exact source syntax?
2. What is allowed?
3. What is rejected?
4. What target shape does it lower into?
5. Which shared helper owns the logic?
6. Which tests prove the behavior?

If a feature cannot answer those questions cleanly, it is not ready to be part of the language.

## 15. Status

This document describes the intended and currently implemented language standard as reflected by the parser, semantic passes, generators, runtime helpers, and tests in this repository. When code and documentation diverge, the repository must be updated so the language has one coherent contract again.
